Standard exercises (Weeks 2–7).

Twelve exercises to deepen the mental model. Eight are codebase reads; the last four are browser DevTools deep-dives — the single fastest way to stop guessing how the web actually works. Read-only relative to TAP•IP. Pick one per week; bring questions to your 1:1.

01 15 min

Read a repository.

Pick any file in frontend/src/lib/repositories/. Read 10 min. Write a paragraph: what entity? What method to list everything? What you DON'T see (hint: tenant ID checks).

02 20 min

See how a URL turns into a folder.

The idea: when you open TAP•IP at app.tap-ip.com/acme/engine/patents, where does that page actually live in the code? Next.js uses a clever trick: the URL path = the folder path. This exercise makes you see it with your own eyes.

Steps:

  1. Open the tp-ipms folder in VS Code.
  2. In VS Code's file explorer (left sidebar), navigate to frontend/src/app/.
  3. You'll see a folder called [tenantSegment]. The square brackets mean "this part of the URL is a variable" — at runtime, this gets filled in with the customer's name (like acme).
  4. Open it. Inside, you'll see (authenticated). The parentheses are a Next.js trick to group routes without changing the URL. Just open it and keep going.
  5. Now you'll see three subfolders: lab/, engine/, desk/. Those are the three workspaces from chapter 01.
  6. Open engine/. List the subfolders you see (you should find patents/, trademarks/, inventors/, etc.). Each one is a real URL on the live site.

What you should notice:

  • The URL app.tap-ip.com/acme/engine/patents matches the folder path app/[tenantSegment]/(authenticated)/engine/patents/. The brackets and parens don't show up in the URL; everything else does.
  • Each "leaf" folder (the ones that don't have more subfolders) has a file called page.tsx. That's the actual React page Next.js renders when a user visits that URL.

Deliverable: Pick the workspace that interests you most (Lab, Engine, or Desk). In a note, list its top-level subfolders. Pick one of them and open its page.tsx file. Read the first 30 lines. Write down one thing you understood and one thing that confused you. Bring both to your next 1:1.

Browser DevTools deep-dive

Exercises 09–12: see what the browser actually does.

Every web developer alive runs the browser DevTools dozens of times a day. They turn the browser from a black box into a glass box — you can see exactly what HTML rendered, what got sent over the network, what's stored on your machine, and what's broken. Open with Cmd+Option+I (Mac) or F12 (Windows/Linux). See chapter 06 for the tab-by-tab tour.

09 20 min

Inspect like a designer (Elements tab).

The idea: the page you see is just HTML + CSS that the browser turned into pixels. The Elements tab lets you read the HTML, see which CSS rules apply to any element, and edit either one live to see what changes. Designers use this to prototype. Engineers use it to debug.

Steps:

  1. Open TAP•IP locally and log in. Navigate to any patents list page.
  2. Open DevTools (Cmd+Option+I) and click the Elements tab.
  3. Click the little cursor icon in the top-left of DevTools (or press Cmd+Shift+C). Now hover over any button or text on the page — DevTools highlights the matching HTML element.
  4. Click on a button. The Elements panel jumps to that <button> tag. On the right, you'll see the Styles panel showing every CSS rule that applies.
  5. In the Styles panel, find a color value (like background-color: rgb(99, 102, 241)). Click it. Change it to red. The page updates instantly. Nothing is saved — refresh and it's back to normal.
  6. Try changing some text: find a heading in the HTML panel, double-click the text, type your name, hit Enter.

What you should notice: the browser is fundamentally a layout engine that turns HTML + CSS into pixels. Everything you see is these two things. There's no magic.

Deliverable: Pick any TAP•IP page. Make three live edits in the Elements tab (a color change, a text change, hide an element by setting display: none). Screenshot the before/after. Bring to your next 1:1 with the question: "How would I make this change permanent?" (Hint: chapter 06 + the frontend/src/components/ tour.)

10 35 min

Watch one request fly (Network tab).

The idea: the Network tab logs every HTTP request the browser makes. Status codes, URLs, headers, request bodies (payloads), response bodies, timing — all of it. This is the single most important DevTools skill. When something on a page "doesn't work," the Network tab tells you whether the browser even asked the server, what it asked, and what the server said back.

Steps:

  1. Open TAP•IP locally. Open DevTools and click the Network tab.
  2. Check the Preserve log checkbox at the top — otherwise the tab clears on each navigation.
  3. Click Clear (the 🚫 icon) to wipe the log. Then navigate to the patents page. Watch the rows flood in.
  4. Find one row whose Type column says document or fetch. Click it. A side panel opens with five sub-tabs: Headers, Payload, Preview, Response, Timing.
  5. Headers — see the URL, the HTTP method (GET / POST / etc.), the status code (200 / 404 / etc.), and the headers the browser sent + the server returned. Cookies live here.
  6. Payload — only present on POST/PATCH/PUT. The actual data the browser sent up (the form values, the JSON body).
  7. Response — the raw bytes the server sent back. Could be HTML, JSON, or anything else.
  8. Timing — how long each phase took (DNS lookup, connection, server processing, download).
  9. Now do something that writes: create a new idea or patent. Watch the Network tab. Find the request with method POST and a 2xx status. Open it.
  10. Look at its Payload. That's chapter 05 in real life — your form data flying to the server. Look at its Response. That's the ActionResult coming back.

What you should notice:

  • One page load is rarely one request — it's dozens. HTML, CSS, JavaScript bundles, fonts, images, then any data fetches the page makes.
  • Every request has a status code — and you can spot failures (red rows) instantly.
  • The browser is making these requests on your behalf the whole time you're using the web. You just couldn't see them before.

Deliverable: Create one new idea in TAP•IP with Network tab open. Find the POST request that handled the create. In a note, record: (a) the URL, (b) the HTTP method, (c) the status code, (d) what was in the Payload, (e) what came back in the Response. Then refresh the page and find one request that returned a status code that wasn't 200 (try 304 or 204 — both are normal). Write down what the code means.

11 20 min

Debug like an engineer (Console tab).

The idea: the Console is a live JavaScript prompt running on the current page. You can read errors, inspect any variable in scope, and run any JavaScript expression you want. When code on a page breaks, this is where the explanation appears. When you want to understand what some code is doing, you sprinkle console.log(value) calls in it and read them here.

Steps:

  1. Open TAP•IP. Open DevTools, click the Console tab.
  2. If any errors show in red, read one. Errors are usually a sentence in English plus a file path and line number. Click the file path — DevTools jumps to the source.
  3. Click into the prompt at the bottom (next to the >) and type: 2 + 2. Press Enter. You should see 4. The Console runs any JS expression.
  4. Try: window.location.href. Returns the current URL as a string.
  5. Try: document.title. Returns the page title (the text in the browser tab).
  6. Try: document.querySelectorAll('button').length. Returns the count of <button> elements on the page. (DevTools' Elements tab shows you HTML structure; the Console can query it.)
  7. Now navigate around the app. Watch the Console for any warnings or errors that pop up. Most are harmless (deprecation warnings, etc.), but some real bugs surface here first.

Deliverable: Find one error or warning in the TAP•IP console during normal use. Copy the full message. In a note, write: what file did it point to? What line? Is it scary or harmless? (You don't have to fix it — just learn to read it.) Bring to your 1:1.

12 25 min

See what's stored about you (Application tab).

The idea: HTTP is technically stateless — every request is independent and the server doesn't "remember" you. So how does the web know you're logged in across page loads? The browser stores small pieces of data — cookies, localStorage, sessionStorage — and sends them along with requests. The Application tab shows everything the current site has stored. This is also where you spot privacy issues, hung-cache problems, and "why is the app showing me stale data" mysteries.

Steps:

  1. Open TAP•IP, logged in. Open DevTools, click the Application tab (Chrome) or Storage (Firefox).
  2. In the left sidebar, find Cookies → click the TAP•IP domain. You'll see a table of cookies. Look for one whose name suggests authentication (Supabase uses names like sb-...-auth-token). Notice its HttpOnly column is checked — that means JavaScript on the page cannot read it; only the server can. That's a security feature.
  3. Click Local Storage → the TAP•IP domain. You'll see key/value pairs. Local storage persists across browser restarts. Session Storage (just below) clears when the tab closes. Together they're how the page "remembers" things on your machine without involving the server.
  4. Try a thought experiment: delete the auth cookie. Refresh the page. You'll be kicked back to the login screen — because that one cookie was the proof-of-login the server was checking on every request.
  5. Open the IndexedDB section. Some apps use this for large local databases (offline-first apps). TAP•IP probably has little here; that's fine — but Excalidraw (chapter 02's whiteboard) does use it.

What you should notice:

  • Cookies get sent to the server with every request. They're the standard way to handle login state.
  • localStorage stays on your machine — never sent to the server. Good for user preferences, theme settings, draft text.
  • sessionStorage dies when the tab closes. Good for temporary state during a single visit.
  • "Clear site data" in this tab is the nuclear option when something gets stuck.

Deliverable: In a note, list (a) how many cookies TAP•IP stores for you, (b) which one is the auth cookie (the one that, if deleted, logs you out), (c) any item in localStorage and what you think it's for. Bring the list to your 1:1.

Stretch goal

Ship your own product.
By week 10.

Same stack as TAP•IP. Founder mentorship on demand. Your project, your call.

The roadmap is five weeks. Each milestone is bounded — small enough to finish in a week with normal intern hours. Pitch the idea to the founder in week 6 for sanity-check (not approval — it's your project).

Week 06

Pick an idea.

Use /superpowers:brainstorming + the BD Playbook ideation techniques. Pick something narrow you could build in 3-4 weeks. Pitch to founder for sanity-check.

Week 07

Scaffold the stack.

Your own GitHub repo. Free Supabase project. Free Railway service. npm create next-app@latest with TypeScript + Tailwind + App Router. Push the Hello World. Get the deployed URL.

Week 08

Add a table + one feature.

Pick ONE entity (tasks, notes, bookmarks). Use Drizzle ORM. Create a table. Build one server action that inserts a row. Build one page that lists rows. Deploy.

Week 09

Make it shareable.

Add auth (Supabase Auth has a Next.js quickstart). Add a landing page using brand voice principles from TAP•IP. Optionally buy a domain (~$12/yr).

Week 10

Show someone.

Share with one real user (friend, classmate, family). Watch them try it. Take notes. Present at your end-of-summer review: what you learned + what you'd do with another 10 weeks.
