Chapter 03 · ~10 minutes

Tenant security, four layers deep.

Why multi-tenant SaaS is hard — and how TAP•IP makes it structurally safe.

The hard problem.

TAP•IP is a multi-tenant app. Acme Corp's patents and Globex's patents both live in the same Postgres database, in the same tables. Every row has a tenant_id column. The most important security guarantee in the entire app:

No query Acme runs can ever see Globex's data, and vice versa.

Quick SQL primer. SQL (pronounced "sequel" or "S-Q-L") is the language you use to talk to a database. A query is one instruction. The most common one is "give me rows from this table" — written like this:

SELECT * FROM patents WHERE tenant_id = 'acme-uuid';

In English: "give me every column from the patents table, but only rows where the tenant_id column equals acme-uuid." The WHERE part is the filter. Without it, you get every patent from every customer.

This sounds obvious. It's hard. One missing WHERE tenant_id = ? in any SQL query, anywhere in the codebase, would leak every customer's data. So TAP•IP has four layers of belt-and-suspenders defense to make sure that filter never gets forgotten.

(The ? is a placeholder — when the code runs, it gets replaced with the actual tenant ID for safety reasons. You'll see this pattern everywhere; it's called a "parameterized query.")

Think of TAP•IP as a bank that holds every customer's account in one giant vault. Every transaction is stamped with an account number. The bank's systems refuse to let any teller pull data without an account number, and the vault itself refuses to open without the right key. Forget the account number? Nothing happens.

Three database roles.

TAP•IP doesn't run its own database server — we rent one from Supabase. Inside that one Postgres instance, we use three different "roles" with different powers. A role is like a user account — it controls what queries you're allowed to run.

app_user 99% of traffic

The role 99% of user requests run as. Bound by RLS policies, meaning Postgres only shows it rows that belong to the current tenant. If your code accidentally queries another tenant's data, Postgres returns zero rows — no error, no leak.

app_admin_user ~1%

For cron jobs, webhooks, and rare cross-tenant admin work. This role bypasses RLS. We use it sparingly — it removes the safety net.

postgres migrations only

The superuser. Only used for running migrations. Should never connect from app code.

In TAP•IP code, you almost never write raw SQL or talk to the database directly. Instead, two patterns wrap every database call:

🧰 Repositories — one class per entity.

A repository is a TypeScript class that owns every read and write for one kind of thing. PatentRepository owns patents. MatterRepository owns matters. There's no scattered SQL — if you want patents, you go to the Patent class.

🪪 Context — a "who are you" object.

A context is a small TypeScript object passed around that says "this code is running on behalf of user U at tenant T." It looks like { tenantId, userId, role }. Every repository takes a context when you build it.

So a real "list all patents" call in TAP•IP looks like this — clean, no SQL, no database plumbing:

// frontend/src/app/actions/patents.ts const repo = new PatentRepository(ctx); // ctx = { tenantId, userId, role } const patents = await repo.list();

Under the hood, PatentRepository.list() calls a helper called tenantDb() — which is what actually picks the right database role and sets the tenant filter. That helper looks like this:

// frontend/src/lib/db/index.ts (helpers used inside repositories) // 99% of code — RLS-bound, scoped to the current tenant via ctx tenantDb() → connects as app_user, applies RLS // Rare admin only — bypasses RLS (cron, webhooks) adminDb() → connects as app_admin_user

You'll see this layered pattern unfold in chapter 04. The point for now: app code calls a repository method · the repository chooses tenantDb() or adminDb() · the database does the RLS check.

RLS — the vault door.

RLS (Row-Level Security) is a Postgres feature where you write a small policy that runs automatically on every query. The policy decides which rows the user can see.

Here's the policy that protects the ip_assets table:

database/alembic/versions/008_rls_policies.py -- Every SELECT, INSERT, UPDATE, DELETE runs through this: CREATE POLICY ip_assets_tenant_isolation ON ip_assets USING (tenant_id = current_tenant_id()) WITH CHECK (tenant_id = current_tenant_id()); -- current_tenant_id() returns the value SET in the transaction. -- If our code forgets to set it, queries see zero rows. Safe by default.
RLS is the vault door, not just the lobby guard. Even if the lobby guard (our app code) waves someone through by mistake, the vault won't open without the right key. Postgres is the vault; the app is the lobby.

This is the architecture's most-loved feature. A developer can write SELECT * FROM patents with no WHERE clause, and the database automatically filters by the current tenant. The safety isn't optional — it's structural.

RLS is why TAP•IP can have hundreds of customers in one database and still sleep at night. CLAUDE.md §15 walks through the full RLS classification of every table if you want depth later.

How the tenant_id actually crosses the boundary.

So far we've said: "RLS checks tenant_id = current_tenant_id() on every query." Natural follow-up: how does Postgres know which tenant the current request is for? There has to be a handoff — your TypeScript code knows the tenant (from the user's session); Postgres needs to be told. Here's exactly how that happens.

The TypeScript side: tenantDb().

Every tenant-scoped query goes through one helper. It opens a transaction, sets a Postgres config variable (called a GUC — Grand Unified Configuration), then runs your queries.

frontend/src/lib/db/index.ts export async function tenantDb<T>(callback) { const tenantId = await requireTenantId(); // 1. read tenant_id from auth cookie/JWT // ...UUID format check (injection guard)... return db.transaction(async (tx) => { await tx.execute(sql`SELECT set_config('app.current_tenant_id', ${tenantId}, true)`); return callback(tx); // 2. now run Drizzle queries inside this tx }); }

The true flag means transaction-scoped — when the transaction commits, the GUC resets. That's critical for connection pooling: the next request that grabs this connection starts fresh.

The Postgres side: current_tenant_id().

One tiny SQL function reads the GUC back out. Every RLS policy calls it.

database/alembic/versions/001_schema_core.py CREATE OR REPLACE FUNCTION current_tenant_id() RETURNS UUID AS $$ SELECT NULLIF(current_setting('app.current_tenant_id', true), '')::UUID; $$ LANGUAGE SQL STABLE;

If the GUC was never set (because someone forgot to use tenantDb() and queried directly), current_tenant_id() returns NULL, the policy never matches, and queries return zero rows. Safe by default — you can't accidentally leak across tenants by skipping the GUC.

How the Repository ties it together.

The TenantContext passed into a repository's constructor (chapter 04 covers this in depth) is built by the tenantAction wrapper from the same JWT. When the repo calls tenantDb(), both sides re-read the JWT. The base class asserts they match — defense against someone hand-constructing a context with a different tenant:

frontend/src/lib/repositories/base.ts protected async query<T>(fn) { return tenantDb(async (db) => { const ambient = await requireTenantId(); // from JWT if (ambient !== this.ctx.tenantId) { // from constructor throw new Error('tenant mismatch — refusing to query'); } return fn(db); }); }
Full round-trip · in one breath

Login → Supabase issues JWT (containing tenant_id) → stored in an HttpOnly cookie. Request → server action runs → tenantAction wrapper reads cookie, builds TenantContext → new Repo(ctx) → repo.query() → tenantDb() opens a transaction → set_config('app.current_tenant_id', uuid, true) stashes the tenant on the transaction → Drizzle query runs → Postgres applies the RLS policy → policy calls current_tenant_id() → reads the GUC → filters rows where tenant_id matches → commits → GUC resets. Done.

Why a GUC and not just a WHERE clause everywhere?

Because the whole point of RLS is "even if app code forgets." A GUC + policy applies to every query that touches the table, automatically. Forget a WHERE tenant_id in one Drizzle call out of hundreds and you've leaked across tenants. With the GUC pattern, Postgres enforces it server-side — TypeScript only has to remember to call tenantDb() once per request. The rest is structural.

And because the connection authenticates as app_user (not superuser), RLS actually applies — superusers bypass RLS, so accidentally running cross-tenant queries on the wrong connection role would be a real risk if we used postgres or app_admin_user. The three-role separation from earlier in this chapter is what makes the GUC pattern bulletproof.
