Chapter 06 · Interactive · ~22 minutes

When the server talks first.

Chapter 05 was a single request — user clicks, server answers. But real apps update without you doing anything. The whiteboard fills in your teammate's edits. The notification badge appears. The Stripe receipt confirms a payment. Five playback experiences across the patterns that make all of this work.

Why this matters. The internet was designed for one direction: browsers ASK servers for things, servers REPLY. Browsers can't be "called." Pushing updates the other way — server → browser — required clever tricks. Two questions to keep in mind: (a) how does data get from server to browser? Answers: polling, SSE, WebSockets. (b) how does the server-side code know an event happened at all? Answers: pub/sub (internally) and webhooks (when external services tell us). All five animations below.

The collab server is a separate process from the Next.js app. Lives in its own Docker container, deployed as its own Railway service. Why? Because long-lived connections need different scaling than HTTP request handlers. Mixing them would make both worse.

Animation 4 of 5

Behind the curtain — how the server knows to push.

Animation 2 (SSE) showed the browser receiving an event from the server. But how does the SERVER know an event happened? You wrote a server action that inserts a patent. How does the server also know to tell every other browser in the tenant about it?

Answer: pub/sub — short for "publish/subscribe." One piece of code publishes an event to a named channel. Other pieces of code subscribe to that channel and react. They don't know about each other. They don't import each other. They communicate through the channel.

TAP•IP's pub/sub uses Postgres NOTIFY/LISTEN — a tiny pub/sub feature built into the same database that already stores the data. Watch a single patent-create flow all the way through.

Setup the animation assumes

The collab server you just met in animation 3 (whiteboard) also handles entity-change broadcasts. It's a single Socket.IO container that runs multiple feeds.

When the user logged in and the React app booted, the browser opened one Socket.IO connection to the collab server. After auth, the server joined that connection to the room entity-changes:{tenantId}:all — the general feed for this tenant. If the user navigates to a whiteboard, the SAME connection also joins a whiteboard:{boardId} room. One pipe, multiple rooms.

By the time the animation starts, that connection has been sitting open for minutes. The browser is silently waiting. Now watch what happens when a teammate creates a patent.

Three things this teaches:

  • Decoupling. The server action doesn't import the collab server. Doesn't know it exists. Just calls publish().
  • One channel, many subscribers. Today only the collab server LISTENs. Tomorrow we could add a Slack notifier, a search-index updater, an analytics warehouse — without touching the publisher.
  • Why pg_notify and not Redis? Postgres is already there. One fewer system to deploy + monitor. Trade-off: the NOTIFY payload is capped at 8KB (we enforce 8000 bytes with a margin). For TAP•IP's events that's plenty; for video frames it wouldn't be.
Animation 5 of 5

Webhooks — when someone else needs to tell us.

Animation 4 was internal: TAP•IP code talking to TAP•IP code. But sometimes an external service has news for us. Stripe finishes processing a payment. GitHub merges a PR. SendGrid bounces an email. We're not going to poll Stripe every 2 seconds asking "is the payment done yet?" — and Stripe can't open a long-lived SSE connection to our app.

The answer is a webhook: we register a URL with Stripe, and when they have news for us, they POST to that URL. It's the inverse of chapter 05's request flow — instead of us calling them, they call us.

TAP•IP doesn't use webhooks yet — but every product you build that takes payments, integrates with GitHub, sends emails, or talks to any modern SaaS will use them. Here's the flow.

Three rules you can't break with webhooks:

  • Signature verification is mandatory. Stripe signs every POST with an HMAC of the body using a secret only you and Stripe know. Skip the check and anyone on the internet can forge a "payment received" message and grant themselves a subscription.
  • Return 200 fast. If Stripe doesn't get a 200 within ~10 seconds, they assume failure and retry — with exponential backoff for up to 3 days. Don't do slow work inside the handler. Take the message, queue it, return 200, do the work elsewhere.
  • Be idempotent. Retries mean you may receive the same event twice. Check the event ID against a "seen" list; ignore duplicates.

Bridge to chapter 06 in one breath: once the webhook handler updates the DB, it can also call publish() — the same pub/sub mechanism from animation 4. So a Stripe webhook can drive an SSE push to the user's browser, and the user sees "Plan upgraded ✓" without refreshing. That's the whole chapter, in one feature.

Same pattern, different events

Zoom: the email case (it's the one you can't avoid).

Sending email looks simple — you call the API, it returns 200. But "the API accepted your message" is not "the user received it." The events that happen after the send only reach you through webhooks. And some of them have legal must-handle implications.

Legal must-handles

email.bounced — the address is invalid. You MUST stop sending to it, or Gmail / Outlook tank your sender reputation and your other emails start landing in spam for everyone.

email.complained — recipient marked your email as spam. You MUST add them to a suppression list — required by CAN-SPAM (US) and PECR (UK).

email.unsubscribed — recipient clicked unsubscribe. You MUST honor within 10 business days — CAN-SPAM federal law. Each violation = up to $51,744 fine.

The flow for a typical bounce, end to end:

1. // User clicks "Forgot password" Your server → POST https://api.resend.com/emails { to: "alic@example.com", // typo last month at signup subject: "Reset your password", ... } Resend ← 200 OK { id: "msg_abc123" } // Resend queued it. NOT delivered yet. 2. // Resend attempts SMTP delivery to example.com Resend → example.com SMTP: RCPT TO:alic@example.com example.com ← 550 5.1.1 User unknown 3. // Resend POSTs a webhook to YOUR pre-registered URL Resend → POST https://app.tap-ip.com/api/webhooks/resend Resend-Signature: t=1733180000,v1=... { "type": "email.bounced", "data": { "email_id": "msg_abc123", "to": "alic@example.com", "bounce_type": "hard", "reason": "User unknown" } } 4. // Your server: • Verifies signature // same HMAC pattern as Stripe • Marks alic@example.com as bounced=true in DB • Returns 200 OK to Resend • Next "send to alic@example.com" call → SKIP // no wasted send, no reputation damage

The shape mirrors the Stripe flow exactly — the only differences are which events and which DB columns. Once you understand one webhook integration, you understand them all.

For your own product

Every email-sending SaaS pays the webhook tax. You don't get a choice. The moment your product sends real emails to real users, you'll need a /api/webhooks/resend route handler (or whichever provider you use) doing exactly the flow above. Build it on day 1, not when you get your first bounce-related Gmail reputation drop.

When to use what.

Polling

Good for: updates that can wait several seconds (refreshing a leaderboard, checking job status). Bad for: chat, presence, collab editing. Easy to implement — no special server infra. The default before SSE was widely supported.

SSE (Server-Sent Events)

Good for: server → browser push, one-way. Notifications, live updates, AI token streaming, entity-change feeds. Auto-reconnects on disconnect. Works over plain HTTP — no protocol upgrade. TAP•IP uses SSE for AI streaming + the entity_changes pipeline.

WebSockets (Socket.IO)

Good for: bidirectional, low-latency. Collab editing, multiplayer games, real-time drawing. Both sides can push. Requires more infra (separate server process). TAP•IP uses Socket.IO for the whiteboard.

Pub/Sub (internal)

Good for: server-side code that needs to notify other server-side code without coupling. Decouples producers from consumers. Sits underneath SSE/WebSocket — answers "how did the server know to push?" TAP•IP uses pg_notify + LISTEN inside the collab server.

Webhooks (external)

Good for: external services pushing news to us. Stripe payment completed, GitHub merged a PR, SendGrid bounced an email. The external service POSTs to a URL we pre-registered. Always verify the signature. Always return 200 fast.

In one breath

Browser pulling on a timer = polling (simple, wasteful, laggy). Server pushing one-way over a held-open connection = SSE (efficient, auto-reconnects, great for notifications + AI streaming). Bidirectional, both sides push = WebSocket (great for collab editing). Internal pub/sub = how the server-side code knows an event happened in the first place — one component publishes, others subscribe, nobody imports anybody. Webhooks = the external version of pub/sub — Stripe / GitHub / SendGrid POSTs to a URL we registered. TAP•IP uses SSE for AI streaming + entity-change feeds, Socket.IO for whiteboard collab, and pg_notify as the pub/sub channel underneath. Webhooks aren't in TAP•IP yet — but they're in every product you'll ever build.
