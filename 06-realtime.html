Chapter 06 · Interactive · ~15 minutes

When the server talks first.

Chapter 05 was a single request — user clicks, server answers. But real apps update without you doing anything. The whiteboard fills in your teammate's edits. The notification badge appears. How does that work? Three playback experiences, three architectures.

Why this matters. The internet was designed for one direction: browsers ASK servers for things, servers REPLY. Browsers can't be "called." Pushing updates the other way — server → browser — required clever tricks. Three tricks now dominate: polling, SSE, and WebSockets. Each animation below shows one in action.

One open connection. Zero wasted calls. Sub-second latency. TAP•IP uses SSE for the AI chat streaming — the model's tokens appear in your UI as they're generated, not after the whole response finishes. The entity_changes pipeline also fans out through SSE to update lists when other users add rows.

The whiteboard — three users, one canvas.

SSE is one-way: server → browser. For real-time collaboration, the browser also needs to PUSH (your edits) and the server needs to FAN OUT (to all the other browsers). That's WebSockets — a bidirectional connection. TAP•IP's whiteboard uses Socket.IO (a WebSocket library) running in a separate "collab server" container.

The collab server is a separate process from the Next.js app. Lives in its own Docker container, deployed as its own Railway service. Why? Because long-lived connections need different scaling than HTTP request handlers. Mixing them would make both worse.

When to use what.

Polling

Good for: updates that can wait several seconds (refreshing a leaderboard, checking job status). Bad for: chat, presence, collab editing. Easy to implement — no special server infra. The default before SSE was widely supported.

SSE (Server-Sent Events)

Good for: server → browser push, one-way. Notifications, live updates, AI token streaming, entity-change feeds. Auto-reconnects on disconnect. Works over plain HTTP — no protocol upgrade. TAP•IP uses SSE for AI streaming + the entity_changes pipeline.

WebSockets (Socket.IO)

Good for: bidirectional, low-latency. Collab editing, multiplayer games, real-time drawing. Both sides can push. Requires more infra (separate server process). TAP•IP uses Socket.IO for the whiteboard.

In one breath

Polling = browser pulls on a timer (simple, wasteful, laggy). SSE = server pushes one-way over a long-lived HTTP connection (efficient, auto-reconnects, great for notifications + AI streaming). WebSockets = both sides push over a bidirectional connection (great for collab editing). TAP•IP uses SSE for the AI chat streaming + the entity-change live updates, and Socket.IO over WebSockets for the whiteboard collab. The collab server is its own Railway service because long-lived connections scale differently than HTTP request handlers.
