The pipeline, stage by stage.

Raw patent data goes in one end; four query-ready artifacts come out the other. Here's each stage.

Overview

Five stages, two machines, one clean result.

The pipeline isn't a single script — it's a sequence of well-defined stages. Each stage has one job, a clear input, and a clear output. Understanding them separately makes it easy to debug when something goes wrong, and easy to re-run just the stage that changed.

The next sections walk each stage in order. By the end you'll see exactly why each step exists and how they fit together into the lakehouse pattern introduced in D1.

Stage 1 — Ingest

Pull the whole corpus, not one record at a time.

The first job is simple to describe: get the data. But the how matters a lot. We don't call a live per-record API, asking "give me patent #1, give me patent #2 …" — that would take years and would hammer the patent offices' servers. Instead, we pull bulk data packages: large files that each contain millions of records, published by the patent offices specifically for this purpose.

Two sources feed the pipeline today:

🇪🇺
EPO BDDS · public area

European Patent Office — bulk DOCDB data.

The EPO's Bulk Data Delivery Service (BDDS) has a public area that requires no authentication and has been free since 2025. It publishes DOCDB-style bibliographic data — titles, abstracts, applicants, classifications — in large structured packages covering the whole EPO corpus.

Because it's anonymous and free, we can automate pulls without worrying about token rotation or rate-limit accounts. The public endpoint is stable and designed for bulk use.

🇺🇸
USPTO · bulk data

United States Patent and Trademark Office — bulk XML.

The USPTO publishes weekly bulk data dumps covering granted patents and published applications. Each dump is a large XML file — or a set of them — representing everything granted or published that week. We pull these packages rather than using the live per-record search API.

Pulling bulk packages means one transfer brings in tens of thousands of records at once, with no per-record overhead and no risk of hitting query rate limits.

The key principle: we are consumers of bulk data publications, not scrapers. Both EPO and USPTO maintain these packages for exactly this use case — researchers and services that need the full corpus.

Stage 2 — Normalize & resolve

Many formats → one common shape.

EPO and USPTO don't use the same data format. EPO BDDS gives us structured bibliographic XML in DOCDB style. USPTO gives us its own XML schema that's evolved over decades and has its quirks. A record from the EPO and a record from the USPTO describing the same invention look completely different on disk.

Normalization is the stage that fixes this. Every incoming record — regardless of source — gets mapped to a single internal schema: a common set of fields with consistent names, consistent date formats, consistent classification codes. After this stage, downstream code doesn't need to know whether a record came from EPO or USPTO.

Alongside normalization, this stage is also where the entity-resolution spine attaches. "Samsung Electronics Co., Ltd." and "SAMSUNG ELECTRONICS CO LTD" and "Samsung Electronics" are the same company — but they appear as different strings in the raw data. The entity-resolution layer (covered in depth in D4) resolves these into a single canonical identity, so analytics can roll up all of a company's filings regardless of how the name was spelled in each jurisdiction.

This stage is deliberately kept simple: clean, map to schema, attach entity spine. Nothing fancy. The next two stages do the heavy analytical work.

Stage 3 — Land it in the lake

Write Parquet to the object store. That's the source of truth.

Once a record is normalized, we write it to Cloudflare R2 as a Parquet file. Parquet is the standard columnar file format for analytics data: it stores each column separately, compresses well, and lets query engines skip columns they don't need. An analytics engine reading "filing year" and "company name" doesn't have to touch the abstract text — it just skips that column entirely.

This is the ELT pattern: Extract, Load, Transform — land first, transform in place with SQL afterward. It's the opposite of old-school ETL (transform before loading). Why ELT?

  • Cheap to land. Raw Parquet on R2 costs very little. You're not paying an expensive warehouse to ingest it.
  • Re-runnable. If a transform step has a bug, you fix the SQL and re-run it against the files already in the lake. You don't need to re-pull everything from the source.
  • Files are the source of truth. The lake is the ground truth. Every serving artifact downstream is built from these files and can be rebuilt at any time. If the serve box explodes, you rebuild from the lake — nothing is lost.

Think of R2 as the master copy and everything downstream as derived. You can always re-derive the derived things; you can't re-derive the source.

Stage 4 — Build the serving artifacts

Four specialized artifacts. Each answers a different kind of question.

The lake is the source of truth but it's not optimized for serving queries at speed. One build step (running on a big rented machine — more on that in the next section) reads the Parquet files and produces four specialized artifacts, each tuned for a different query pattern:

Artifact 1
Tantivy search index.

Answers: "find me patents about battery thermal management." Full-text keyword search across hundreds of millions of titles and abstracts — the kind of query that needs an inverted index, not a database scan.

Artifact 2
Lean lookup DB · SQLite

Answers: "give me everything about patent EP1234567." Point lookups by patent number, plus citation graph edges and family groupings. A SQLite file with B-tree indexes — built so a query jumps straight to the row instead of scanning. (DuckDB builds this file; SQLite serves it.)

Artifact 3
Slim analytics table.

Answers: ad-hoc analytical queries — GROUP BY, filters, time-series — that don't fit the pre-aggregated cube. A lean, columnar table with only the fields analytics needs, stripped of the heavy text columns.

Artifact 4
The cube.

Answers: "rank every company by filings per year, by country." Pre-aggregated totals across all the dimensions people filter on. Covered in depth in D3 — the fastest path from question to leaderboard.

Each artifact is built once during the rebuild cycle, then published to R2. The always-on serve box pulls them and uses them to answer queries without ever touching the raw lake again.

Build vs serve — two different machines

A big ephemeral box builds. A small always-on box serves.

This is the key operational idea behind the pipeline, and it flows directly from the lakehouse principle: separation of storage and compute.

Building the serving artifacts requires a lot of memory and disk — you're reading hundreds of millions of rows, joining tables, building a full-text index. That's an expensive machine to leave running all the time, especially when you only need to rebuild once a week. So we don't leave it running.

Instead, we rent a big machine only while building. When the rebuild starts, a large ephemeral box spins up, reads the Parquet files from R2, builds all four artifacts, publishes them back to R2, and then shuts down. The whole thing runs while you're not watching and costs only for the hours it actually runs.

The serve box is small because it doesn't need to rebuild anything — it just loads pre-built artifacts into memory and answers queries against them. Its job is fast reads, not heavy computation.

R2 is the shared storage layer between the two machines. That's what makes this work: the build box and serve box never need to be running at the same time. The object store is the handoff point. Build, publish to R2, shut down. Serve box notices new artifacts on next startup, swaps them in. Clean separation.

Reproducible rebuilds. Because the lake files are the source of truth and every build step is just SQL over Parquet, the entire serving layer can be torn down and rebuilt from scratch at any time. That's exactly what the weekly refresh does: spin up the build box, re-run the pipeline end to end, publish fresh artifacts, shut down. Nothing is special-cased or hand-maintained. If a bug is found in the build logic, you fix the SQL, re-run, and the artifacts are correct. No manual patching of a live database.
