Chapter 09 · ~12 minutes

The lifecycle of a feature.

A feature or bug doesn't just appear on production. It flows through a predictable cycle — ticket, triage, branch, commit, review, merge, deploy — across the services from chapter 07. Here's the full path, end to end.

Why this matters. Every change to TAP•IP — every bug fix, every new feature, every refactor — follows the same loop. Once you know the shape, your first ticket isn't scary. You know what each step is for and where you are in it.

The loop, in one picture.

Five actors. Six steps. About a day of wall-clock time for a small fix; longer for big features. Read the diagram once before the deep-dive — you'll come back to it as a map.

A feature lifecycle is like a restaurant order. The diner (founder, user) places it. The expediter (kanban board) sequences it. A cook (you) picks the ticket and works it. A second pair of eyes (CodeRabbit + founder) plates it for safety. The runner (Railway) carries it out. Same shape, every dish.

Step by step.

Each card below zooms into one phase of the loop above.

A
Where work comes from

1 · The ticket gets filed.

Every change at TAP•IP starts as a GitHub Issue. No issue, no work. This isn't bureaucracy — it's a paper trail so nothing falls through the cracks, and so every decision is searchable later.

Work comes from three places:

  • Founder roadmap — the next feature on the build plan.
  • User feedback — "this would be useful," "this is annoying."
  • Bugs caught in review or production — something broke.

Issues come in three sizes:

🐛 Bug

Narrow scope. Something broke. Example: "Patent edit modal won't save Korean characters."

✨ Feature

Medium scope. New capability. Example: "Add cost waterfall to family page."

🏛️ Epic

Large scope. Multi-week initiative spanning many tickets. Example: "Frontend repository pattern migration (#850)."

A good ticket has: a clear title, a "why" in the body, and explicit Acceptance Criteria (AC) — a bulleted checklist of what "done" means. AC is the contract. If a bullet isn't checked, the ticket isn't done.

You can read every TAP•IP ticket at github.com/carlostap-ip/tp-ipms/issues. Browse a few. Find one labeled good first issue if it exists.

B
Triage & the kanban board

2 · Where the ticket sits before you pick it up.

TAP•IP uses kanban, not sprints. Why? Small team, fast iteration, founder-driven priorities. Sprints add ceremony that doesn't pay off until you're 6+ engineers.

The board has columns:

flowchart LR
  BL[📥 Backlog
everything filed]
  RD[🟢 Ready
well-defined · pick from here]
  IP[🔨 In progress
someone's working on it]
  RV[👀 In review
PR open · awaiting feedback]
  DN[✅ Done
merged + deployed]
  BL --> RD --> IP --> RV --> DN
  • Backlog — incoming. Could be anything from a one-line idea to a fully-spec'd epic.
  • Ready — the founder has triaged it and confirmed it's well-defined enough to work on. Has AC. This is the column you pick from.
  • In progress — someone (you) is actively working on it. Drag the card here when you start.
  • In review — you've opened a PR. The card sits here while CodeRabbit + founder review.
  • Done — merged + auto-deployed.

Founder triages incoming issues weekly, sometimes daily for hot bugs. If a ticket isn't in "Ready" yet, you don't pick it up — ask the founder if it should be.

C
Picking up

3 · Claim the ticket.

  1. Pick from "Ready" — read the title, then the body, then the AC. Every bullet in AC is a checkbox you'll need to hit.
  2. Assign yourself — click "Assignees" on the GitHub issue, pick your handle.
  3. Move the card to "In progress" — drag it on the board.
  4. Re-read the AC. If anything is ambiguous, ask the founder before you start coding. Asking after costs everyone time.

📌 Founder rule: "Stick to AC. If you find scope you want to defer, ask first." Unfiled "we'll do this later" mentions are worse than no mention. If something is out of scope, file a separate ticket.

D
The dev loop · your laptop ⇄ GitHub

4 · Branch, code, commit, push.

This is the longest phase — anywhere from 30 minutes to several days depending on ticket size. The shape is the same every time.

# 1. Get the latest main branch
git checkout main
git pull origin main

# 2. Create a feature branch (name it after the ticket)
git checkout -b feat/intern-1042-fix-korean-chars

# 3. Code · use Claude Code · follow patterns from chapter 04 + 10

# 4. Run gates locally · BEFORE pushing
cd frontend
npx tsc --noEmit              # type check (mandatory · 0 errors)
npm test                       # jest unit tests
docker compose up -d           # dev server · smoke test in browser

# 5. Commit · clear message · imperative voice
git add path/to/changed/files
git commit -m "fix(patent-edit): preserve unicode chars on save"

# 6. Push the branch to GitHub
git push -u origin feat/intern-1042-fix-korean-chars

Branch naming convention: <type>/<handle>-<issue#>-<short-slug> — e.g. feat/sam-1042-fix-korean-chars. The type prefix is feat, fix, chore, docs, or refactor.

Commit messages follow the same type(scope): message shape — fix(patent-edit): ..., feat(cost-engine): .... Short. Imperative. Future-you grepping git log will thank you.

E
Open the PR

5 · Submit your work for review.

A Pull Request (PR) is "I want my branch's changes merged into main. Please review." On GitHub, after you push a branch, a yellow banner appears: "Compare & pull request." Click it.

What goes in a good PR:

  • Title — short summary, under 70 characters. Mirrors the commit message style.
  • Summary — 2–3 bullets describing what changed and why.
  • Test plan — checklist of how a reviewer can verify it works.
  • Link the ticket — include Fixes #1042 in the body. GitHub auto-closes the issue when the PR merges.
# Example PR body
## Summary
- Patent edit modal now uses utf8mb4 encoding on save
- Adds regression test for non-ASCII title input

## Test plan
- [ ] Edit a patent · set title to "특허 제목 테스트"
- [ ] Save · reload · title persists
- [ ] Run frontend/src/__tests__/patent-edit.test.tsx · all green

Fixes #1042

If your branch isn't ready for review yet, open it as a draft PR — same workflow, but no one will be paged. Flip it to "Ready for review" when it's done.

You'll learn the shortcut for this in chapter 10 — the /ship command in the TAP•IP plugin runs the gates + opens the PR for you.

F
Code review · humans + AI

6 · CodeRabbit + founder.

TAP•IP uses two reviewers on every PR:

🤖 CodeRabbit (AI)

An AI reviewer that auto-comments within minutes of opening the PR. Catches obvious bugs, style issues, missing tests, security concerns. Sometimes wrong — push back if you disagree. Not blocking unless founder agrees with it.

👤 Founder (human)

Final say. Reviews the diff, asks questions, requests changes, or approves. Faster than industry average — usually within a few hours during work time.

How to address feedback: push more commits to the same branch. The PR updates automatically. You don't open a new PR.

# Address review feedback
git add changed/files
git commit -m "fix: address review · null-check on row.id"
git push                          # pushes to the existing PR branch

The review cycle repeats until both reviewers are happy. Most PRs go through 1–3 rounds. A couple rounds is normal — review isn't personal, it's how good code happens.

You'll meet the /babysit-pr command in chapter 10 — it auto-pushes your PR through review cycles with Claude Code's help. Use it after you open your first PR.

G
Merge & deploy

7 · Founder hits "Squash and merge."

Once both reviewers approve, the founder clicks Squash and merge. This collapses all your branch's commits into one commit on main — clean history. Your branch is then deleted (the PR remembers it forever).

The moment the merge happens, the deploy pipeline from chapter 07 kicks in:

  GH[🐙 main branch updated]
  WB[Railway webhook fires]
  RW[🚂 Railway builds
Docker container
~3-5 min]
  PD[🌐 Production
change is live]
  GH --> WB --> RW --> PD
  • Railway detects the push to main.
  • Builds a new Docker container with your code.
  • Runs a quick smoke check.
  • Rolls it out — zero downtime — to live production.
  • Total time: ~3–5 minutes for a frontend change.

The ticket auto-closes (because of Fixes #1042). Card moves to "Done" on the board.

H
Verify · close out

8 · Confirm it works in production.

Don't trust "merged" as "shipped." Always verify.

  1. Wait for Railway to finish (you'll see ✅ on the PR).
  2. Open production. Exercise your change. Does it work?
  3. If yes: comment on the ticket "shipped, verified." Move on to your next ticket.
  4. If no: roll it back. Railway has a one-click rollback to the previous version. Then file a bug ticket on yourself, debug, repeat the loop.

📌 Founder rule: "Test visually before committing UI. Verify the page renders before claiming done." Type checks and unit tests don't catch broken UX. Always click through the feature in a browser.

Two helpful shortcuts.

You'll meet these in chapter 10, but they're worth flagging now since they automate parts of the loop above:

  • /ship — the TAP•IP plugin command that runs the type check + tests + opens the PR for you. Steps D + E above.
  • /babysit-pr <number> — automatically pushes your PR through CodeRabbit feedback cycles. Steps F (the review-fix loop).

Neither replaces understanding the loop. They speed it up after you understand the steps.

For your own product

Same loop. You play every role.

Solo project? You're both the founder filing tickets and the engineer working them. GitHub Projects gives you a free kanban board on any repo. CodeRabbit has a free tier. Railway auto-deploys. The shape of the loop is identical — file a ticket, branch, commit, PR, self-review, merge, deploy, verify.

The habit is what matters. The lifecycle is what separates "I built a thing once" from "I ship things every week."
