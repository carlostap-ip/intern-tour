Chapter 11 · ~12 minutes

Why the code looks like this.

SOLID · DRY · Clean Code. The principles that shape every file you'll read.

You've seen the layered architecture — server actions, repositories, typed contexts, RLS. Why is the code organized this way and not some simpler way? Three foundational ideas from software engineering shape almost every line.

You don't need to memorize the definitions. But knowing the names lets you read PRs and engineering writing without flinching.

A. SOLID — five disciplines, one acronym.

SOLID is a checklist of five principles for writing maintainable object-oriented code. Introduced by Robert C. Martin ("Uncle Bob") in 2000. Each letter is one principle.

S
Single Responsibility.
SRP — one class, one job.

Every class should do one thing, and have only one reason to change.

A specialist desk for patents. Not a "general legal stuff" desk that handles patents AND matters AND tasks.

In TAP•IP: PatentRepository only handles patents. MatterRepository only handles matters. Never one giant DataRepository.

O
Open / Closed.
OCP — open to extension, closed to modification.

Code should be open to extension but closed to modification.

Adding a new aisle to a grocery store without rearranging existing aisles.

In TAP•IP: adding a new IP-asset type doesn't require modifying every existing repository. We extend the ip_assets table with a new discriminator value (§17 of CLAUDE.md).

L
Liskov Substitution.
LSP — subclasses behave like their parents.

A subclass should be usable anywhere its parent is used, without surprises.

If someone asks for a vehicle, both a Car and a Truck should work — same wheels, both go forward.

In TAP•IP: all repositories extend TenantScopedRepository. Anywhere code accepts a TenantScopedRepository, any specific repository works.

I
Interface Segregation.
ISP — narrow interfaces beat wide ones.

Don't force code to depend on methods it doesn't use.

Don't make every Animal implement bark() — only Dogs need that.

In TAP•IP: the typed-context family (TenantContext / ServiceContext / PublicContext) is segregated. Code that only needs PublicContext can't accidentally touch tenant data.

D
Dependency Inversion.
DIP — depend on interfaces, not implementations.

Code should depend on interfaces, not on specific implementations.

Your code asks for "a way to send email," not "Gmail." You can swap Gmail for SendGrid without rewriting the caller.

In TAP•IP: repositories accept a TenantContext interface. The interface is the contract; the actual implementation is injected at runtime.

B. DRY — Don't Repeat Yourself.

If the same logic appears in three places, extract it to one place. From The Pragmatic Programmer (1999).

DRY is like writing an FAQ instead of answering the same question in 50 separate emails. Write the answer once; point everyone at the same page.

In TAP•IP: tenant filtering happens in ONE place (the tenantDb() helper), not in every query. Permission checks happen in ONE place (requirePermission), not duplicated in every action. The §19 canonical-helper pattern is DRY taken seriously — even small repeated patterns get extracted.

Counterpoint worth knowing: DRY can be overdone. Three lines that look similar but represent different concepts shouldn't be merged — premature abstraction is worse than duplication. CLAUDE.md puts it well: three similar lines is better than a premature abstraction.

C. Clean Code.

A set of habits popularized by Robert C. Martin's book of the same name (2008). The goal: code reads like prose.

Good naming.

Variables and functions named for what they mean, not what they are. activePatents, not arr.

Small functions.

A function should fit on your screen. If it doesn't, split it.

No useless comments.

If you need a comment to explain WHAT, rename instead. Comments are for WHY.

One concept per line.

Don't pack three operations into one statement.

Tests are first-class.

Test code gets the same care as production code.

Boy Scout Rule.

Leave the campground cleaner than you found it. If you touch a file, clean up something small.

In TAP•IP: file names use clear kebab-case. Functions tend to be small. Tests live alongside the code they test (__tests__/). The codebase isn't perfect, but the principles are aspirational and the team takes them seriously.

Why these matter for you.

Two reasons. First, when you read TAP•IP code and wonder "why is this split into so many files?" — these principles are the answer.

Second, when you build your own product in the stretch goal, these are the rules that keep your code maintainable past week one. Skip them and your project becomes unsalvageable around 2000 lines of code.

Recommended starter: read the first three chapters of Clean Code by Robert C. Martin. Or watch any of his free talks on YouTube. ~3 hours total, repays itself the first week.
