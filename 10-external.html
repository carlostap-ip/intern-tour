The outside world.

How TAP•IP talks to patent offices, AI providers, and other apps. The advanced layer that connects everything we don't run ourselves.

Most of these are advanced — you won't touch them in your first few weeks. Read this when you want to know how TAP•IP plugs into the rest of the internet.

A. Patent office APIs.

TAP•IP's whole job is managing IP that lives in real government databases. We don't store patent filings ourselves — we pull live data from the actual patent offices. Three matter most:

🇺🇸
backend/uspto/

USPTO — United States Patent and Trademark Office.

The biggest one. The USPTO exposes a few HTTP APIs: PEDS (Patent Examination Data System) for application metadata + status, PAIR (Patent Application Information Retrieval) for office actions and correspondence, and the public TM database for trademarks. TAP•IP wraps these in a Python client at backend/uspto/clients/ and uses them to pull live status updates, file new applications, and check trademark availability.

Rate limits are real (USPTO caps at ~120 requests/min for some endpoints), so we cache aggressively and retry with backoff.

🇪🇺
Open Patent Services

EPO — European Patent Office.

The European equivalent. EPO's Open Patent Services (OPS) is a REST API that gives us PCT (international filing) data plus European national-phase status. Auth is OAuth2 — we get a token, expire it every hour, and refresh.

🌍
PATENTSCOPE + ePCT

WIPO — World Intellectual Property Organization.

The PCT (Patent Cooperation Treaty) infrastructure. WIPO doesn't have as developer-friendly an API as USPTO or EPO — most of what we use is XML feeds and scheduled bulk downloads. Used for international filings and deadline tracking across 25 jurisdictions.

The pattern: every patent-office integration follows the same shape — a Python client class wraps the HTTP protocol, retries with exponential backoff, caches responses for a sensible TTL, and surfaces errors through the AppError envelope (chapter 09's preview). When you read backend/uspto/clients/, you're reading the canonical version of this pattern.

B. AI provider APIs.

TAP•IP calls Anthropic (Claude) and OpenAI (GPT-5) APIs for every AI feature — drafting patent claims, summarizing prior art, parsing invoices, helping brainstorm sessions.

The split we covered briefly in chapter 02 lands here:

  • TypeScript-side calls (frontend/src/lib/ai/completion.py) — for one-shot prompts. Returns a single response, no tools, no memory.
  • Python-side calls (backend/paralegal/) — for agentic loops. Multi-step reasoning, tools, memory across turns.

Both go through wrapper layers that handle rate limits, retries, token accounting, and provenance — so callers don't worry about the raw SDK shape. CLAUDE.md §10 is the canonical reference if you want depth.

Your own product almost certainly uses one of these too. Anthropic and OpenAI both have free tiers; both have official Node.js and Python SDKs. The hard part isn't calling them — it's deciding whether you need agents or just one-shot prompts.

C. The MCP server.

MCP is the Model Context Protocol — Anthropic's open standard for letting AI clients (like Claude Desktop, custom agents, or future AI tools) read and write data from your app, with proper auth and scoping.

TAP•IP runs an MCP server at mcp_service/. It exposes a curated set of tools that an authorized AI client can call:

What this means in practice: an inventor can open Claude Desktop, say "jot down an idea about a new fastener design", and Claude will call TAP•IP's create_idea tool to actually create a draft idea in the Lab. No browser open, no manual data entry. The MCP server handles auth (which tenant?) and tenant-scoping (the idea belongs to that user, not someone else's).

Tools currently exposed by TAP•IP's MCP server (from mcp_service/tools/):

  • create_idea, search_ideas, get_idea_details — Lab idea management
  • add_notebook_entry, list_notebook_entries, update_notebook_entry — notebook notes
  • create_whiteboard, list_whiteboard_options — visual canvas creation
  • link_notebook_entry_to_idea, promote_notebook_entry_to_idea — cross-linking

Why this matters strategically: as more inventors and IP teams use AI assistants daily, the MCP server lets TAP•IP show up inside their existing AI workflow rather than forcing them to open another browser tab. It's also forward-looking — if Claude or another assistant gets agentic memory, TAP•IP's tools become part of that memory automatically.

D. Briefly: webhooks, email, OAuth.

A few more external integrations you'll see in the code but don't need to understand deeply yet:

  • Email (Resend) — outbound transactional email (account verification, notifications, share invites). The Resend API key is stored in platform_api_credentials and managed in the System Admin Portal.
  • Gmail + Google Calendar (OAuth) — when a user connects their Google account, TAP•IP can read scheduled meetings (for prep / disclosure reminders) and send draft emails. OAuth tokens live in mcp_service/oauth/.
  • Webhooks — TAP•IP listens for incoming events from a few services (Stripe for billing, USPTO bulk-update notifications). Webhook handlers are regular FastAPI routes on the Python backend.
For your own product

You'll wire up external services from day one.

Even a tiny project usually calls 2–4 external APIs. Common ones:

  • Anthropic or OpenAI — almost every modern app has an AI feature. Both have official SDKs and generous free tiers.
  • Resend or Postmark — outbound email. Both free up to a few thousand emails/mo.
  • Stripe — if you charge money. Stripe Checkout gets you a payment page in 10 minutes.
  • Supabase Auth — already covered; handles login, signup, password reset for free.

Wrap each API in its own client class. Don't sprinkle SDK calls throughout your code — same reason TAP•IP doesn't sprinkle Postgres queries everywhere.
