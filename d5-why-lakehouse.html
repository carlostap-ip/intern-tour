Track II · The data engine · ~6 min

Why the modern lakehouse wins.

Pull the threads together: why this architecture, and not a giant database, is the modern default — and what to steal for your own work.

Five things that make it work

The lakehouse isn't magic. It's five ideas working together.

Each of the previous pages in this track introduced one piece of the architecture. Here they are as a set — because the power is in how they fit together, not in any single piece alone.

Idea 1
Cheap storage is the source of truth.

The object store (Cloudflare R2) holds all the raw Parquet files. It costs little, scales without effort, and doesn't go down. Everything else is derived from these files and can be thrown away and rebuilt. The lake is permanent; the serving layer is disposable.

Idea 2
Columnar files make scans cheap.

Columnar Parquet means an engine like DuckDB reads only the columns a query needs and skips the rest. Scanning hundreds of millions of filing-year values doesn't require touching the abstract text sitting next to them on disk. Column pruning + compression makes this fast.

Idea 3
Pre-aggregate the hot queries.

Even fast scans take time across hundreds of millions of rows. Pre-aggregation — building the cube once at build time — means the most common analytical questions (leaderboards, breakdowns by year and country) are answered by a single row lookup, not a full scan. Build once, read instantly.

Idea 4
Right engine per query shape.

No single engine is best at everything. Tantivy handles full-text search (inverted-index queries); DuckDB handles analytics and point lookups (columnar scans and GROUP BYs). Routing queries to the right engine is what makes each one fast — and avoids the trap of forcing one tool to do everything.

Idea 5
Storage and compute are separate.

The build machine and the serve machine are not the same machine, and they don't need to be. Build big (lots of RAM, lots of disk) only while building. Serve small (minimal footprint) always. The object store is the handoff point between them. This is the core structural idea that makes "throw away the serving layer and rebuild" cost-effective.

None of these ideas is new. What's new is that all five are now cheap enough to combine at scale — object storage is near-free, open-source engines like DuckDB and Tantivy are production-ready, and Parquet is the universal interchange format. The lakehouse is what you get when you assemble them intentionally.

The payoff

Reproducibility & cost. The boring superpower.

Because the object store holds the lake files and every artifact is built from them with SQL, the serving layer has a property that most production databases do not: it is completely disposable. You can delete every artifact — the DuckDB files, the Tantivy index, the cube — and rebuild the whole thing from scratch. Nothing is lost, because the lake files are still there.

This sounds mundane until you've worked with a system where it isn't true — where the production database is the only copy of transformed data, where a migration gone wrong means a weekend of manual recovery, where "what would happen if I re-ran this from scratch?" is a question nobody wants to answer. The lakehouse answers it trivially: spin up a build box, re-run the pipeline, done.

The cost consequence follows directly. If the serving layer is disposable, you only pay for it when it's earning its keep. The always-on cost of a small serve box is modest; the build box runs only during the rebuild window and then shuts off. There's no requirement to run expensive compute continuously just to keep data warm. The lake is the always-on layer, and it's cheap by design.

The practical test. A good sanity check for any data system: "If the serve layer exploded right now, how long would it take to recover, and would any data be permanently lost?" In a lakehouse built this way, the answer is: rebuild time, and no. That's the benchmark worth aiming for.

What's next

The same spine extends further.

The architecture described across this track — lake files as source of truth, purpose-built engines, separation of storage and compute — is a foundation, not a ceiling. The same structural spine naturally extends toward graph queries over citation and patent-family networks, semantic search over the full-text corpus, and signals beyond patents altogether (financial disclosures, R&D spend data, other data layers that attach to the same canonical entity map). These are directions, not timelines. The point is that none of them require redesigning the foundation — they're additional artifacts built on top of the same lake files, routed through the same query-dispatch pattern, benefiting from the same rebuild discipline. The architecture earns its keep precisely because it stays open to that kind of extension.

For your own project

You rarely need a warehouse to start.

DuckDB plus a folder of Parquet files — or a cheap bucket like R2 — is a real lakehouse on a laptop for roughly nothing. For most projects at intern scale, that's all you need: write your data out as Parquet, query it with DuckDB, and you get columnar performance and SQL expressiveness without standing up any infrastructure at all.

Add pre-aggregation only when a specific query gets slow in practice — measure first, optimize second. Don't build the cube because it sounds impressive; build it because you identified a bottleneck and this is the right fix.

Reach for a dedicated search engine like Tantivy (or Meilisearch, or Typesense) only when SQL LIKE / full-text search gets genuinely slow or limited. The threshold is real user pain, not anticipated pain. The same principles that shape this production system — cheap storage as truth, right engine per query shape, separation of build and serve — apply just as cleanly at a fraction of the scale. Start small, keep the files, and the architecture grows with you.
