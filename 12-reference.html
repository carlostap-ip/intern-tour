Two patterns you'll see in every file.

A. Feature flags as access control.

A "feature flag" is a switch that controls whether a feature is on for a given customer. TAP•IP uses them as access control — each customer subscribes to a package (e.g., "Desk only" or "Full Stack"), and the package determines which features they can access.

Every server action that touches a gated feature calls requireFeature(FEATURES.IPMS_PATENTS) at the top. If the customer's package doesn't include patents, the action throws before any database query runs.

Feature flags are like a gym's tier system. Basic membership = pool. Premium = pool + sauna. Front desk checks your tier at every door.

B. The AppError envelope.

When something goes wrong, TAP•IP never throws raw exception strings to the UI. Errors are wrapped in an AppError envelope — a TypeScript discriminated union with code, category, userMessage, retryable, and requestId fields.

Why? Three reasons. (1) The UI renders a friendly message instead of "ECONNREFUSED at line 47". (2) Errors get logged to a database table with the requestId, so support can find them. (3) Errors get auto-triaged — same category = same trace.

You'll see this in code as actionFail('NOT_FOUND') or actionFail('VALIDATION', { userMessage: "..." }). Never raw throw new Error(...).
