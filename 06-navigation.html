Where things live.

A navigation map of frontend/src/. Find code by name in 60 seconds.

You'll spend a lot of time in frontend/src/. Here's the folder tree and what each piece holds.

frontend/src/ ├── app/ Next.js App Router. URL routes map 1:1 to directories. │ ├── actions/ Server actions (the entry points) │ ├── [tenantSegment]/(authenticated)/ │ │ ├── engine/ The Engine workspace pages │ │ ├── lab/ The Lab workspace pages │ │ └── desk/ The Desk workspace pages │ └── login/ Login page ├── lib/ Shared toolbox. ~170 folders + files. │ ├── repositories/ One TS class per entity (PatentRepository, etc.) │ ├── db/ Drizzle schema + tenantDb/adminDb helpers │ ├── auth/ Authentication helpers │ ├── errors/ AppError envelope │ ├── features/ Feature flag registry │ ├── ai/ AI infrastructure │ ├── cost-engine/ Cost engine logic │ └── (much more) ├── components/ React UI components (buttons, modals, forms) ├── contexts/ React Context providers (client-side state) ├── hooks/ Custom React hooks (useTenant, useFeature, etc.) ├── types/ TypeScript type definitions ├── utils/ Small utility functions └── middleware.ts Runs on every request (auth checks, redirects)

The 80/20.

You'll find what you need 80% of the time with these four:

src/app/

"Where's the page for /engine/patents/5?"

src/lib/repositories/

"Where's the function that talks to the database?"

src/components/

"Where's that confirmation modal?"

src/contexts/

"How does the app know what tenant I'm in?"

Naming conventions.

  • Files are kebab-case: patent-repository.ts, not PatentRepository.ts.
  • .ts = pure TypeScript. .tsx = TypeScript with JSX (React components).
  • Imports use the @/ alias for src/:
import { PatentRepository } from '@/lib/repositories/patent-repository';

In VS Code, the 60-second speedrun.

  • Cmd+P → type a file name → jump to it.
  • Cmd+T → type a symbol name (function, class) → jump to its definition.
  • Cmd+Shift+F → search across all files.
  • Right-click a function name → "Go to Definition" or "Find All References".

That's the entire navigation toolkit. The rest is muscle memory.

And in the browser: DevTools.

Knowing where code lives is half the job. The other half is seeing what it does at runtime. That's Browser DevTools — a panel built into every modern browser that lets you inspect the live page, watch network requests, see errors, and debug JavaScript.

Open it on any page: Cmd+Option+I on Mac, F12 or Ctrl+Shift+I on Windows. Or right-click anything → Inspect.

Five tabs you'll use weekly:

Elements

Inspect the HTML & CSS.

See the live HTML tree, click any element to highlight it on the page, edit CSS in real time to test styling changes. Right-click → "Inspect" jumps you straight to the element you clicked.

When you'd use it: "why is this button mis-aligned?" / "what color is this?" / "where does this Tailwind class come from?"

Network

Watch every HTTP request.

Every page load and every button click that talks to the server shows up here as a row. Click a row to see the URL, method (GET, POST, …), status code, payload, and response. This is how you watch chapter 05's request flow happen for real.

When you'd use it: "did my server action actually fire?" / "what data came back?" / "why is this page slow?"

Console

See errors. Run JavaScript live.

Errors and warnings appear here in red. You can also type JavaScript directly and run it — document.title + Enter prints the current page title. Devs use console.log("here", someVar) in their code to print debug messages; they show up here.

When you'd use it: "the page crashed — why?" / "what value does this variable have?" / "why doesn't my click handler fire?"

Sources

Set breakpoints. Step through code.

Open any JavaScript file the browser is running, click a line number to set a "breakpoint," then reload — execution pauses on that line. Step forward one line at a time, hover variables to see their values. The grown-up version of console.log.

When you'd use it: when a console.log fest isn't enough or you need to understand a complex call chain.

Application

Cookies, localStorage, service workers.

See cookies (where login sessions live), localStorage / sessionStorage (small client-side preferences), and any service workers / cache the page uses. Right-click → "Clear" wipes a value if you want to test the logged-out flow without logging out.

When you'd use it: "am I actually logged in?" / "where's my session token?" / "test what an unauthenticated user sees."

Three shortcuts that pay for themselves the first day: Cmd+R in DevTools = reload the page. Hold Shift while reloading to bypass the cache. In the Network tab, check the Disable cache box so you always see fresh requests while DevTools is open.

Chrome's docs are great if you want depth: developer.chrome.com/docs/devtools. But honestly, you'll learn 80% of what you need by clicking around for 30 minutes.
