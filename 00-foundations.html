First, the basics.

If you've never built a website, this chapter is your runway. Nine concepts the rest of the tour assumes you know — each in plain language, no jargon.

Already familiar with web development? Skim or skip. The tour proper starts at chapter 01. This page is a safety net for first-time readers — nine concepts that come up over and over.

1. What's a server?

A server is just a computer that's always on and reachable over the internet. It runs a program that listens for incoming requests ("hey, send me the homepage" or "save this form") and sends back responses.

Your laptop is technically a server too, but it's not always on, not always reachable, and not optimized for handling traffic. Real servers live in data centers — companies like Railway, AWS, Vercel rent them to you so you don't have to buy your own.

A server is like a 24/7 phone line for your business. Customers (browsers) call in, the line is always picked up, and someone always answers with the right information.

When this tour says "the Next.js server" or "the Python server," it means: a computer in Railway's data center running a Next.js program (or a Python program), waiting for browser requests.

2. What's a database?

A database is a program that stores data in an organized way and lets other programs ask questions about it ("give me all patents owned by Acme Corp").

The data lives in tables — like spreadsheets, but with strict rules about what kind of data each column can hold and how tables relate to each other. The most popular open-source database is PostgreSQL (we just say "Postgres"). TAP•IP uses Postgres.

Table

A spreadsheet with named columns. Example: a patents table with columns id, title, filing_date, tenant_id.

Row

One entry in a table. One patent in the patents table is one row.

Query

A question you ask the database. "Give me all patents where tenant_id is acme-uuid" is a query.

SQL

The language for writing queries. Pronounced "sequel" or "S-Q-L."

A database is like a filing cabinet plus a librarian. The cabinet holds the rows. The librarian (SQL) answers questions like "find me everything filed by Acme in 2024." You ask in English-ish; she pulls the right folders.

Here's what one table looks like — three columns, four rows. Every row is one patent. Every column has a strict type.

erDiagram
  PATENTS {
    uuid id PK "primary key"
    varchar title "the patent name"
    date filing_date "when filed"
    uuid tenant_id FK "owning customer"
  }
  TENANTS ||--o{ PATENTS : owns
  TENANTS {
    uuid id PK
    varchar name "Acme, Globex, etc"
  }

The diagram above shows two tables — tenants (customers) and patents — and the line between them means "one tenant can own many patents." That's how databases let you connect rows across tables. Postgres calls this a foreign key relationship.

3. What's a framework?

A framework is a pre-built foundation for building software. It handles the boring, repetitive parts ("how do I serve a webpage?", "how do I route URLs?") so you can focus on what makes your app unique.

Next.js is the framework TAP•IP uses for the frontend. It's built on top of React (a library for building user interfaces). Together they handle:

  • Rendering pages with HTML/CSS/JavaScript.
  • Routing — making /engine/patents show the patents page automatically.
  • Server-side rendering — building the page on the server so it loads fast.
  • Server actions — letting the browser call server functions like local ones.

Without a framework, you'd have to write all of this yourself. With Next.js, you just write the parts that are unique to your app.

A framework is like buying a pre-built house frame instead of cutting every 2×4 from scratch. The plumbing and electrical rough-in is done; you just choose the wallpaper, the appliances, the layout of the rooms.

4. Frontend vs backend.

Frontend = the code that runs in your browser. What the user sees and clicks. Made of HTML, CSS, and JavaScript.

Backend = the code that runs on the server. Reads from the database, runs business logic, sends data back to the frontend.

TAP•IP's frontend is mostly Next.js + React. The backend is split: most of it lives inside the Next.js server (as server actions), and a small piece lives in a separate Python (FastAPI) server for AI and heavy computation.

Frontend is the storefront — the displays, the signs, the cash register. Backend is the warehouse and the accountants — out of sight, doing the actual work.

5. What's a URL?

A URL (Uniform Resource Locator) is the address you type in the browser bar — like https://app.tap-ip.com/engine/patents/5. It tells the browser which server to talk to, on which port, asking for which thing. Every URL is a mini-instruction.

A URL has up to six parts. Most you don't see day-to-day, but you'll meet all of them eventually:

https://app.tap-ip.com:443/engine/patents/5?status=pending#claims
└──┬───┘ └──────┬─────┘└─┬─┘└──────┬──────────┘└──────┬──────┘└──┬──┘
protocol   domain (host) port    path          query string  fragment

Protocol

https:// — how browser and server agree to talk. https is encrypted; http is plain text. Always https in production.

Domain (host)

app.tap-ip.com — the server's name. DNS translates it into an IP address (a numeric server location), like a phone book lookup.

Port

:443 — which program on that server. See the callout below.

Path

/engine/patents/5 — which thing on the server. With Next.js, this matches a folder path inside src/app/.

Query string

?status=pending&page=2 — extra parameters the server can read. Like passing arguments to a function via the URL. See the example below.

Fragment

#claims — a spot to scroll to within the page. Never sent to the server; the browser handles it locally.

More on query strings.

The query string is everything after the ?. Each parameter is a key=value pair, joined with &. Multiple parameters work like keyword arguments to a function:

https://app.tap-ip.com/engine/patents?status=pending&jurisdiction=US&page=2&sort=filed_desc
↓ the server sees four parameters
status = "pending"
jurisdiction = "US"
page = "2"
sort = "filed_desc"

The server reads the query string and uses it to filter, paginate, or sort whatever data it sends back. Same URL path, different query string = different data. Open the Network tab in DevTools (chapter 06) and you'll see query strings everywhere.

A few gotchas: spaces become %20 or +; special characters get percent-encoded (the %XX notation). The browser handles this automatically when you submit a form — but you'll see encoded URLs in the wild.

About ports.

A single computer can run many programs at once — and several of them might want to listen for network traffic. Port numbers are how the operating system tells them apart, like apartment numbers in a building. When traffic arrives on port 443, the OS hands it to whichever program is listening on 443.

Web traffic has two defaults nobody types because they're always assumed:

  • Port 80 — plain http://
  • Port 443 — encrypted https://

You'll see other ports all the time when working locally. TAP•IP's dev environment uses these:

http://localhost:3000 → Next.js frontend dev server
http://localhost:8001 → Python (FastAPI) backend
http://localhost:5432 → Local Postgres (via Docker)
http://localhost:6006 → Storybook (UI component preview)

localhost means "this computer" — your laptop talking to itself. Different ports = different programs running on it.

A URL is a mailing address. Protocol = delivery service (FedEx vs USPS). Domain = the building. Port = the apartment number. Path = the resident's name. Query string = a note on the envelope. Fragment = which page of the magazine to flip to.

6. What's an HTTP request?

An HTTP request is how a browser talks to a server. Every time you click a link, submit a form, or load a page, your browser sends an HTTP request and the server sends back an HTTP response.

Requests come in a few flavors (called methods or verbs):

  • GET — "give me this page / data"
  • POST — "here's some new data, save it"
  • PUT / PATCH — "update this existing data"
  • DELETE — "remove this data"

When the tour says "the browser sends a POST to the server action," it means: the browser packages your form data into an HTTP POST request and sends it to a specific URL on the server. The server processes it and sends back a response (e.g., "patent created, here's the new ID").

About request payloads (POST / PATCH bodies).

For GET and DELETE, the request is mostly just "the URL plus headers" — there's no body. But for POST, PUT, and PATCH, the browser also sends a request body (often called the payload) — the actual data being submitted. Two common formats:

JSON — what server actions + modern APIs use

POST /actions/createPatent
Content-Type: application/json
{
"title": "Adaptive Heat Sink",
"jurisdiction": "US",
"filing_date": "2026-06-15",
"inventor_ids": [42, 57]
}

Form-encoded — old-school HTML forms

POST /actions/createPatent
Content-Type: application/x-www-form-urlencoded
title=Adaptive+Heat+Sink&
jurisdiction=US&
filing_date=2026-06-15

The server's response will also have a body — usually JSON describing what got created, what changed, or what went wrong. The Network tab in DevTools shows you both halves: what you sent (Payload tab) and what came back (Response tab). That's exercise 10.

Notice query string vs request body: a query string lives in the URL itself (after the ?) and is visible in the browser bar. A request body rides separately, isn't visible in the URL bar, and can be much larger. Query string = "which thing am I asking for?" Body = "here's the data I'm sending up."

About status codes.

Those numbers (200, 201, 204) are HTTP status codes — three-digit summaries the server returns saying "here's how it went." The first digit tells you the category at a glance:

2xx — Success

It worked. 200 OK = "here's what you asked for." 201 Created = "I made it." 204 No Content = "done; nothing to send back."

3xx — Redirect

"Look somewhere else." 301 Moved Permanently = "the page moved forever." 302 Found = "temporarily go here." 304 Not Modified = "use your cache."

4xx — You messed up

The browser's fault. 400 Bad Request = malformed. 401 Unauthorized = "log in first." 403 Forbidden = "logged in, but no permission." 404 Not Found = "that doesn't exist." 429 Too Many Requests = "slow down."

5xx — Server messed up

The server's fault. 500 Internal Server Error = "something broke; we don't know what." 502 Bad Gateway = "the server in front called another server that died." 503 Service Unavailable = "we're overloaded."

You'll memorize these without trying. 404 and 500 within a week. The rest follows.

7. JavaScript vs TypeScript.

JavaScript is the language web browsers can run. Every interactive website uses it. It's flexible but has a famous problem: it doesn't check types until the code runs, so you find out at 3 a.m. that you added a number to a string somewhere.

TypeScript is JavaScript with type annotations. You declare what kind of data each variable holds (string, number, custom types). A TypeScript compiler then checks your code before it runs and yells at you if types don't match. Catches a huge category of bugs.

TAP•IP uses TypeScript for everything in the frontend. You'll see file extensions .ts (pure TypeScript) and .tsx (TypeScript with React JSX).

JavaScript is writing a math equation by hand and hoping you didn't make a sign error. TypeScript is doing the same equation with a calculator that flags arithmetic errors before you press equals.

8. What's an API?

An API (Application Programming Interface) is a set of named functions that one program exposes for another program to call. When a server says "you can POST to /api/patents to create a patent," that's an API endpoint.

You'll hear "API" used three ways:

  • HTTP API — the URLs a server exposes for browsers or other servers to call. Most common usage.
  • Library API — the functions inside a library you can call from your own code.
  • External API — some other company's HTTP endpoints (the Stripe API, the OpenAI API).

In TAP•IP, server actions effectively REPLACE most HTTP APIs. You call them like local functions; Next.js handles the HTTP request under the hood.

9. The big idea: three boxes talking to each other.

If you remember nothing else from this chapter, remember this picture:

Browser ⇄ Server ⇄ Database

click · request · query · row · response · render

sequenceDiagram
  participant U as 👤 User
  participant B as 🌐 Browser
  participant S as 🖥️ Server
  participant D as 💾 Database
  U->>B: clicks button
  B->>S: HTTP request
  S->>D: SQL query
  D-->>S: rows
  S-->>B: HTTP response
  B-->>U: shows the result

That's almost every web application ever built. The browser shows things to the user. The server runs your business logic. The database remembers stuff between visits. The three talk to each other via HTTP and SQL.

Everything else in this tour is a zoom-in on this picture.
